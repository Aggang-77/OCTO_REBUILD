# OCTO: 사실적 실시간 문어 시뮬레이터 — 기술 설계 및 개발 명세서

> 문서 유형: 다른 GPT/코딩 에이전트에 제공할 프로젝트 기술 명세 및 작업 지시문  
> 언어: 한국어  
> 목표: **실제 문어의 생체역학과 시각적 변형을 최대한 반영하면서 동일한 문어 10마리를 실시간으로 시뮬레이션할 수 있는 3D 게임**  
> 지향점: 논문 수준의 완전한 생체 재현보다 **물리적 일관성·조작성·성능·확장 가능성**의 균형

## 0. 이 문서를 받은 GPT에게

이 문서는 구현 가능한 기술 명세서다. 추상적인 아이디어 제시에 그치지 말고, 구체적인 자료구조·알고리즘·파라미터·프로파일링·테스트와 실제 실행 결과를 바탕으로 작업한다.

- **기존 프로젝트가 있다면** `README.md`, 현재 진행 상황 문서, 이슈, 빌드 시스템 및 현재 구현을 먼저 확인하고, 작업 폴더·브랜치를 명확히 한 뒤 **기존 변경 사항을 보존**하면서 개발한다. 사용자의 변경 내용을 임의 삭제·덮어쓰기·초기화하지 않는다.
- **기존 프로젝트가 없다면** 재현 가능한 최소 프로젝트부터 구축한다.
- 물리 모델·렌더링 모델·입력/게임 로직을 분리한다.
- 검증하지 않은 성능, 정확도, 통과 여부를 사실로 보고하지 않는다.
- 원본 3D 모델, 기존 아트 에셋이나 엔진 프로젝트가 있는 경우 최대한 재사용하며, 사용하지 못한 자산과 이유를 기록한다.
- 아래 수치들은 **초기 설계값 또는 목표치**이며, 실측 성능이나 검증된 생체 물성값이 아니다. 테스트와 프로파일링 결과로 조정한다.

## 1. 핵심 요구사항

### 1.1 게임플레이

1. 플레이어는 문어의 **8개 팔을 각각 키 하나 또는 여러 키 조합에 매핑**해 제어한다.
2. 키 입력은 관절 각도/좌표의 직접 변경이 아니라, **근육 수축·목표 곡률·목표 신장·능동 강성** 등의 구동 명령으로 바뀌어야 한다.
3. 조작한 팔을 바닥, 벽, 지형, 물체 등에 접촉·부착하고, 그 접촉 반작용으로 문어 몸통을 이동시킬 수 있어야 한다.
4. 각 팔은 독립적인 동작을 하면서도 하나의 몸통에 물리적으로 연결된다.
5. 마우스로 팔의 목표 지점 지정, 팔 또는 문어 전체에 힘을 가해 드래그하는 디버그 조작을 지원할 수 있어야 한다.

### 1.2 물리

1. **중력**, 관성, 질량, 운동량, 감쇠, 충돌, 마찰, 접촉 반작용을 구현한다.
2. 문어 2마리 이상이 서로 충돌하고 서로를 밀 수 있어야 한다.
3. **문어 자체의 팔-팔/팔-몸통 자기 충돌**도 고려한다(연결된 인접 구간은 필요한 만큼 예외 처리).
4. 주변 강체 및 지형과의 충돌, 상자 밀기, 빨판 부착과 해제를 지원한다.
5. 모든 동적 물체의 상호작용은 **한 물리 세계의 시간 적분 및 접촉 해결 과정**에서 일관되게 처리한다. 별도 엔진 간 일방향 좌표 복사는 금지한다.
6. 팔은 **굽힘·비틀림·신장·수축·단면 변형**이 가능해야 한다.
7. 몸통·외투막은 부드럽고 연속적으로 변형된다.
8. 팔의 부피는 근육성 정수압 골격을 근사하도록 **거의 보존**하되, 수치 오차와 실제 재료 특성을 허용한다.

### 1.3 시각적 품질

1. 고품질 GameReady 3D 문어 모델을 이용할 수 있으면 그 외형·재질·빨판을 유지한다.
2. 팔은 관절이 각지게 꺾인 모양이 아니라 유기적으로 휘고 늘어나야 한다.
3. 팔/몸통 표면이 접촉에 따라 눌리고, 다른 방향으로 퍼지는 변형을 가능한 범위에서 재현한다.
4. 빨판, 피부 요철, 광택, 색 및 미세 주름을 표현한다.
5. **물리용 저해상도 모델과 렌더링용 고해상도 모델을 분리**한다.

### 1.4 성능

- 동일 문어 **10마리 동시 시뮬레이션**, 플레이 가능한 프레임레이트를 목표로 한다.
- 1차 목표: **60 FPS**, 프레임 총 16.67 ms 이내.
- 잠정적인 물리 CPU 예산: **문어 10마리 전체 약 5 ms/frame**. 이는 보장된 성능이 아닌 최적화 목표다.
- 기준 하드웨어, 렌더링 품질, 화면 해상도, 오브젝트 수, 접촉 수, 평균/최악 구간 프레임 시간을 함께 기록해야 의미 있는 검증이 가능하다.

## 2. 생체역학적 근거와 필수 운동

문어 팔은 뼈 관절이 아닌 **근육성 정수압 골격(muscular hydrostat)** 이다. 근육 활동으로 단면과 길이가 변화하며, 비압축성에 가까운 조직의 부피 유지가 중요한 특성이다.

| 운동 | 원리의 개략적 근사 | 요구되는 게임 동작 |
|---|---|---|
| Bending (굽힘) | 팔 길이 방향의 비대칭 근육 수축 | 팔 말기, 물체 감싸기 |
| Elongation (신장) | 길이가 늘어날수록 단면 축소 | 멀리 뻗기 |
| Shortening (수축) | 길이를 줄이면서 단면 확장 | 물체/몸통 끌어오기 |
| Torsion (비틀림) | 나선형 사근 등에 의한 비틀림 | 빨판 방향 조정 |
| Variable stiffness (강성 조절) | 근육 활성화에 따른 강성 변화 | 힘을 줄 때 단단해지고, 풀면 흐물거림 |
| Local flattening (국소 압착) | 접촉하중에 따른 단면 형상 변형 | 틈 통과, 바닥에 눌림 |

**중요:** 단지 스프링을 약하게 만드는 것과 '실제 문어처럼 젤리 같은' 모습은 다르다. 체적 압축에는 강하게 저항하지만 굽힘·비틀림에는 유연하고, 근육 구동으로 능동 강성을 바꾸어야 한다.

## 3. 권장 전체 아키텍처

```text
[Keyboard / Mouse / AI]
           |
           v
[Input Mapper & Muscle Controller]
           |   (목표 곡률, 길이, 강성, 흡착 명령)

  |-- Octopus: 8 active continuum arms
  |-- Octopus: deformable body/mantle
  |-- Rigid bodies: boxes, props, obstacles
  |-- Static geometry: floor, level collider
  |-- Broadphase -> Narrowphase contact
  |-- XPBD constraints + rigid/contact coupling
  |-- Integrator + collision/attachment response
           |
           v
[Simulation State -> Render State Interpolation]
           |
           v
[Godot 4 Renderer / GPU Skinning / Shaders]
  |-- High-resolution skin mesh
  |-- Suckers / wrinkles / material
  |-- Camera / UI / gameplay
```

**기본 기술 선택:** Godot 4 + C++ GDExtension + XPBD 기반 연성체/강체 통합 솔버 + Cosserat Rod에서 유래한 팔의 위치·방향·변형 제약. 단, 기존 프로젝트가 다른 스택에 잘 구축되어 있다면 교체 비용을 분석한 뒤 결정한다.

고려사항:

- Godot는 **렌더링/입력/장면/UI** 중심으로 사용한다.
- 동적 물체들 사이의 힘과 접촉은 C++ 물리 세계에서 계산한다.
- Godot 기본 RigidBody와 C++ 자체 솔버를 함께 쓴다면 양방향 접촉과 시간동기화를 명시적으로 해결해야 한다. 해결하지 못한다면 동적 강체까지 자체 솔버로 관리한다.
- 디스플레이 프레임 시간은 가변일 수 있지만 시뮬레이션은 **고정 시간 간격**으로 계산한다. 렌더링만 이전/현재 상태 사이를 보간한다.
- 결정론적 테스트를 위해 고정 시드, 고정 입력 로그, 물리 파라미터 버전 등을 기록한다.

## 4. 팔 모델: Cosserat Rod 근사 + XPBD

### 4.1 이산화

- 문어 한 마리: 팔 8개.
- 팔 하나: 초기값 **12~16개 segment**. 첫 기준은 16개.
- 팔의 각 segment는 중심 위치/방향, 길이 및 유효 단면 상태를 가진다.
- `16 segments × 8 arms × 10 octopuses = 1280 arm segments`.
- 이는 구간 수만 센 값이다. 각 구간의 회전 자유도, 체적 노드, 접촉점 등은 별도로 비용에 포함한다.

### 4.2 상태 표현

개념적으로 구간 `i`에 대하여:

\[
S_i = (\mathbf{x}_i,\mathbf{q}_i,\mathbf{v}_i,\boldsymbol{\omega}_i,a_i,b_i)
\]

- `x`: 중심선 위치
- `q`: 단면의 방향(quaternion 혹은 회전 프레임)
- `v`: 선속도
- `omega`: 각속도
- `a,b`: 타원 근사 단면의 반축

연속체 Rod의 실제 변형에너지를 충실히 푸는 것과 XPBD 위치/회전 제약으로 근사하는 것은 동일하지 않다. 초기 구현은 계산 가능한 XPBD 이산 모델을 우선하고, 필요한 경우 Cosserat Rod의 구성방정식을 더 정밀하게 도입한다.

### 4.3 부피 유지

원형 단면 가정:

\[
V_i \approx \pi r_i^2 L_i \approx V_{i,0}
\]

따라서:

\[
r_i \approx r_{i,0}\sqrt{\frac{L_{i,0}}{L_i}}
\]

타원 단면 확장:

\[
V_i \approx \pi a_i b_i L_i \approx V_{i,0}
\]

이를 **국소 체적 제약**으로 사용한다. 예를 들어 한 방향으로 눌릴 때 `a`가 감소하면 다른 방향 `b`가 증가하게 할 수 있다. 실제 복잡한 접촉 압착은 타원 단면만으로 제한이 있으므로 추가 체적 노드를 선택적으로 활성화한다.

### 4.4 주요 제약

1. 축방향 신장/수축: 인접 구간의 길이와 목표 길이.
2. 굽힘: 인접 프레임 간 상대 회전 또는 목표 곡률.
3. 비틀림: 접선 축을 기준으로 한 상대 회전.
4. 전단: 단면 프레임과 중심선의 상대 방향.
5. 국소 체적: 단면적×구간 길이 유지.
6. 팔-몸통 연결: 팔 뿌리의 위치 및 방향 제약.
7. 수동 형상: 힘이 없을 때 자연스러운 평형 자세로 복귀하는 약한 구속과 감쇠.

각 팔에 균등한 강성을 고정하지 말고, 뿌리와 끝의 단면적 및 물성 차이를 허용한다. 팔의 테이퍼(taper)와 질량 분포가 매우 중요하다.

### 4.5 XPBD 제약 해결

일반적인 스칼라 제약 `C(x) = 0`에 대해, 위치 기반 XPBD의 대표적 식은:

\[
\Delta\lambda = \frac{-C(\mathbf{x})-\tilde\alpha\lambda}{\sum_i w_i\lVert\nabla_i C\rVert^2+\tilde\alpha},\qquad
\tilde\alpha = \frac{\alpha}{\Delta t^2}
\]

\[
\Delta\mathbf{x}_i = w_i\nabla_i C\,\Delta\lambda
\]

- `alpha`: compliance (높을수록 유연).
- `w_i`: 역질량.
- `Delta t`: **실제 제약 풀이 서브스텝** 시간.
- 제약별 `lambda`는 해당 풀이 시간 단계의 반복 과정에 맞게 관리한다.
- 3D 회전 제약은 위 위치 식을 단순 복사하는 대신 **회전 관성 및 quaternion 업데이트**를 고려한 식이 필요하다.

여러 종류의 제약을 순서대로 계산할 때 안정성·수렴 속도·에너지 거동을 프로파일링한다. 반복 횟수를 늘리는 것과 서브스텝을 늘리는 것은 비용/정확도 특성이 다르다.

## 5. 근육 구동 모델과 입력

**절대 규칙:** 플레이어 입력으로 물리 입자/팔 끝 좌표를 직접 순간이동시키지 않는다. 목표 값을 변경하고 물리 솔버가 실제 변위를 산출하게 한다.

구간별 근육 활성도 `u_i(t)`는 `[0,1]`에서 시작할 수 있다.

\[
K_i(t) = K_{\mathrm{passive},i} + u_i(t) K_{\mathrm{active},i}
\]

다만 이것은 **강성 증가의 간략화된 예시**일 뿐이며, 실제 근육 수축력을 완전히 표현하지는 못한다. 별도로 목표 곡률 `kappa*`, 목표 신장률 `epsilon*`, 목표 비틀림 `tau*`를 두어야 한다.

입력 파이프라인:

```text
선택된 팔 / 키 상태 / 마우스 목표
    -> 팔 단위 고수준 명령 (뻗기, 수축, 굽히기, 감싸기, 붙이기)
    -> 근육 활성과 구간별 목표 곡률/길이/강성 분배
    -> XPBD 구동 제약 혹은 제한된 능동 힘/모멘트
    -> 충돌/마찰/반작용과 함께 통합해 결과 계산
```

### 5.1 초기 키 매핑 예시

- `Q W E R A S D F`: 각각 팔 1~8 선택/구동.
- `Shift + 팔 키`: 팔 수축.
- `Ctrl + 팔 키`: 접촉된 빨판의 부착 활성화.
- `Alt + 팔 키`: 능동 강성 증가.
- `팔 키 + 마우스 목표`: 해당 팔을 목표 방향으로 뻗거나 휘기.
- 입력 해제: 활성도를 부드럽게 내리고 수동 강성으로 복귀.

이 매핑은 **시제품용 제안**이다. 최종 게임 조작성은 플레이테스트로 조정한다. 단일 키만으로 3차원 공간의 팔 방향 전체를 정할 수 없으므로 마우스 목표, 카메라 기준 방향, 운동 프리셋 중 하나가 필요하다.

### 5.2 제어 응답

- 목표 변경 시 급격한 과도응답이 없도록 입력 필터·출력 상한·활성도 변화율 제한을 둔다.
- 팔 끝 추종 성능은 `오차 / 도달 시간 / 과도 진동 / 접촉 시 관통`을 함께 측정한다.
- 물체에 막힌 팔은 충돌을 무시하고 목표를 향해 이동해서는 안 된다.
- 손맛을 위해 비물리적 보조 제어를 도입한다면 명시하고, 최소한 운동량 전달과 접촉 일관성은 보존한다.

## 6. 몸통·외투막과 형태 변형

### 6.1 초기 접근

- 몸통은 **저해상도 체적 노드 또는 tetrahedral cage** 기반 변형체.
- 시작값: 약 **100~200개 변형 노드/문어**(수치는 근사 설계안).
- 체적/전단/형태 복원/접촉 제약을 부여한다.
- 팔 8개가 연결되는 지점과 입 주변의 구조적 안정성이 필요하다.
- 팔이 강하게 잡아당길 때 몸통과 팔 뿌리에 반작용이 전달되어야 한다.

### 6.2 중요한 생물학적 주의점

실제 문어의 외투막(mantle)은 속이 단단한 균일 젤리구가 아니다. 내부에 기관 및 물이 드나드는 공간이 있다. 따라서 몸통 전체의 전역 부피를 무조건 강하게 고정하면 비현실적인 거동을 만들 수 있다. 국소 조직 체적 유지와 외투막/공간 변형을 구분한다.

### 6.3 좁은 틈 통과

기본 단계:

- 팔의 국소 타원 단면 변형.
- 몸통 저해상도 체적 변형.
- 충돌체 두께와 실제 시각적 피부 사이의 차이를 과도하게 두지 않는다.

고급 단계(필요할 때만):

- 관통·압착이 발생하는 부분만 국소 체적 메시 세분화.
- 더 정확한 연속체 FEM/P2V/MPM 도입 여부는 **구체적 실패 사례와 성능 측정 결과**를 보고 결정한다.
- P2V 등 별도 용어를 기존 프로젝트에서 사용하는 경우, 기존 문서의 정의를 확인하고 추측으로 해석하지 않는다.

## 7. 충돌·마찰·빨판·반작용

### 7.1 단일 물리 세계

한 프레임 내에서:

1. 동적 문어·동적 오브젝트에 중력 및 외력을 적용.
2. 광역 충돌 탐색(broadphase): 공간 해시, BVH, 또는 엔진 조건에 맞는 구조.
3. 근접 충돌 판정(narrowphase): 구간-표면, 구간-구간, 팔-몸통, 강체-강체.
4. 접촉 법선, 관통 깊이, 마찰 접선 등 접촉 데이터 작성.
5. 구동/연성/강체/접촉 제약을 통합해 반복 해결.
6. 접촉 양쪽 동적 객체의 속도·위치(그리고 각운동량)를 갱신.
7. 상태를 렌더링으로 전달.

접촉 중인 두 동적 객체는 접촉 임펄스/힘에 의한 **동일 크기, 반대 방향의 반작용**을 받아야 한다. 회전 운동에 대해서는 접촉점과 질량중심 사이의 모멘트팔을 고려해야 한다. 단순히 위치를 밀어내기만 하면 운동량 보존이 깨질 수 있다.

### 7.2 세부 충돌

- 문어-지형
- 문어-동적 강체
- 문어-문어
- 문어 자신의 팔-팔, 팔-몸통
- 강체-강체
- 얇고 빠른 팔의 관통 방지를 위해 필요 시 CCD/스윕 또는 서브스텝 개선.
- 팔의 바로 옆 연결 구간은 자기 충돌 후보에서 합리적으로 제외. 떨어진 구간끼리는 허용.

### 7.3 마찰

법선 비관통 제약과 접선 Coulomb 마찰을 근사한다. 팔이 바닥을 디딜 때 미끄러짐·지지력·추진력을 만들어야 한다. 단순히 접촉하면 고정되는 로직은 사용하지 않는다.

### 7.4 빨판

모든 시각적 빨판을 고비용 물리 객체로 만들지 않는다.

- 표면에는 고밀도 빨판 메쉬/인스턴스를 표시.
- 실제 접촉 처리에는 **활성 접촉영역을 대표하는 소수의 부착점**을 사용.
- 초기 예산: **팔당 약 4~8개 후보 부착점**, 필요 시 동적 활성화.
- 유효 접촉 + 사용자 흡착 명령 -> 부착 제약 생성.
- 부착 상태: 최대 접선력/법선 유지력, 유효 접촉 방향, 부착·해제 지연, 시간에 따른 강도 변화를 적용.
- 허용 힘을 넘거나 사용자가 해제하면 부착이 끊어짐.
- 대상이 동적 물체라면 부착점이 대상의 질량·회전 관성에 반작용을 전달해야 함.
- 부착 이후 문어 팔이 접촉점을 당기는 동작으로 문어 몸통이나 물체가 움직여야 함.

빨판의 내부 유체압력/미시 접촉까지 정확히 푸는 것은 초기 범위에서 제외한다.

## 8. 물리와 그래픽 분리

### 8.1 CPU 물리

- 저해상도 rod segments + 몸통 volume cage + 제한된 접촉 노드.
- 연산량이 큰 전체 렌더 메쉬 정점을 물리 입자로 사용하지 않는다.

### 8.2 GPU 렌더링

- 로우폴리 충돌/물리 모델 -> 고해상도 표면 스키닝.
- 팔의 위치·회전·단면 반축을 이용해 표면 정점을 변형한다.
- 몸통은 cage-based deformation, skinning 또는 적절한 형태 보간.
- 팔 뿌리/몸통 연결부에서 메시가 찢어지거나 겹치지 않도록 결합 가중치 설계.
- 물리 업데이트 사이의 **시각적 보간**을 이용해 60 FPS+ 렌더링.

### 8.3 질감

- PBR 피부 재질: wet-looking specular, roughness variation.
- 노멀맵/셰이더로 미세 요철·주름.
- 필요하면 제한적인 SSS 근사 및 색/패턴 변화.
- 빨판은 렌더 메쉬에 자연스럽게 추종시키되 물리 활성점과 일치하는 위치를 유지.
- 실제 문어 모델의 외형과 비례·빨판 배열을 우선 유지.

## 9. 성능 최적화 전략

### 9.1 기본 목표 설정

- 렌더 FPS 목표: 60.
- 기본 물리 스텝: `1/60 s` (조정 가능).
- 초기 물리 서브스텝: 2~4회 (`1/120~1/240 s`에 해당), 안정성 측정 후 조정.
- 초기 팔 구간: 12~16개, 필요 시 팔 뿌리·접촉부 위주 가변 해상도.
- 몸통 체적 노드: 약 100~200개.
- 상세 부착점은 실제 가까운 접촉에서만 활성화.
- 반드시 1/2/5/10마리 비교 테스트.

### 9.2 최적화 우선순위

1. **프로파일링:** broadphase/narrowphase/constraints/렌더 전송/스키닝을 분리 측정.
2. **접촉 후보 축소:** spatial hash/BVH; 중복 pair 제거.
3. **SoA 데이터 구조:** position, rotation, velocity, inverse-mass 배열 연속 배치.
4. **제약 그래프 최적화:** 서로 충돌하지 않는 제약 묶음부터 병렬 계산; 공유 노드에 대한 데이터 경합 방지.
5. **활성 영역 계산:** 움직이지 않는 강체/부착 안정 상태의 비용 절감.
6. **물리 LOD:** 비플레이어/먼 문어의 일부 상세 해상도를 줄이되, 강하게 상호작용하는 객체는 보수적으로 유지.
7. **GPU 스키닝:** 고해상도 정점 변형을 GPU로 이동.
8. **시각/물리 시간 분리:** 렌더 프레임 변화가 물리 안정성에 영향을 주지 않도록 구성.
9. **최악 접촉 장면 스트레스 테스트:** 10마리 전부 충돌하는 상황에서 시간 급증 방지.

### 9.3 보고할 성능 지표

| 지표 | 최소 보고 내용 |
|---|---|
| FPS | 평균, 1% low, 최악 프레임 |
| 물리 CPU 시간 | 평균, p95/p99, 최대값 |
| 렌더 CPU/GPU 시간 | 분리 가능하면 각각 |
| 객체 수 | 문어 수, 총 팔 구간, 강체 수 |
| 충돌 | 후보 쌍 수, 실제 접촉 수, 최대 관통 깊이 |
| 안정성 | NaN/Inf, 발산, constraint 오차 |
| 환경 | CPU, GPU, RAM, OS, 빌드 설정, 해상도 |

**유의:** 60 FPS 달성을 CPU 5ms만으로 보장할 수 없다. 물리·게임로직·렌더 전체를 측정해야 한다.

## 10. 최소 구현 자료구조(예시)

```cpp
struct ArmSegmentState {
    Vec3 position;
    Quat orientation;
    Vec3 velocity;
    Vec3 angular_velocity;
    float half_axis_a;
    float half_axis_b;
    float rest_length;
    float inverse_mass;
    Mat3 inverse_inertia_local;
};

struct ArmActuation {
    float target_curvature_1;
    float target_curvature_2;
    float target_twist;
    float target_stretch;
    float stiffness_activation;
    bool suction_enabled;
};

struct OctopusState {
    ArmState arms[8];
    DeformableBodyState body;
    // 충돌 필터, 렌더 연결, 게임플레이 상태 등
};

struct Contact {
    BodyHandle object_a;
    BodyHandle object_b;
    Vec3 point_a;
    Vec3 point_b;
    Vec3 normal;
    float penetration_depth;
    float friction_coefficient;
    // 구속 임펄스/접촉 지속성 등
};
```

위 코드는 **개념적 구조를 보여주는 예시**로, 선언만으로 실제 물리가 구현되는 것은 아니다. 구현 시 타입·메모리 배치·핸들 유효성·관성 계산·quaternion 정규화 등이 필요하다.

### 10.1 물리 스텝 의사코드

```text
simulate_fixed_step(dt):
    distribute_high_level_controls_to_actuators()

    for each substep h = dt / substeps:
        update_active_muscle_targets(h)
        integrate_external_forces_and_predict_states(h)
        broadphase_pairs = query_broadphase()
        contacts = narrowphase(broadphase_pairs)
        update_suction_attachment_constraints(contacts)

        for iteration in solver_iterations:
            solve_arm_stretch_bend_twist_shear_constraints(h)
            solve_arm_local_volume_constraints(h)
            solve_body_volume_shape_constraints(h)
            solve_root_attachment_constraints(h)
            solve_rigid_body_and_contact_constraints(h)
            solve_friction_and_suction_constraints(h)

        update_linear_angular_velocities_from_corrected_states(h)
        apply_appropriate_velocity_level_restitution_and_damping(h)
        update_sleeping_and_contact_cache()

    publish_simulation_snapshot()
```

정확한 `solve` 순서, restitution(반발), 각속도 업데이트 및 마찰 처리는 선택한 XPBD/강체 결합 방식에 맞게 구현하고 검증해야 한다. 특히 위치 보정에서 유도한 속도만으로 모든 강체 운동량 성질이 자동 보존되는 것은 아니다.

## 11. 단계별 개발 로드맵과 종료 조건

### Phase 0 — 프로젝트 조사 및 기준 확보

- 기존 게임·문서·에셋·브랜치 확인.
- 현재 빌드 및 실행 방법 기록.
- 기존 동작을 영상/스크린샷/로그로 기준 확보.
- 정적 메시/물리 콜라이더/리깅 구조 분석.
- 기존 실패 상황(특정 tick/접촉 오류 등)이 있다면 재현 테스트로 고정.

**종료 조건:** 동일 커밋에서 빌드/실행을 재현할 수 있고, 기존 통과/실패 항목이 분리 기록됨.

### Phase 1 — 팔 하나의 기본 물리

- 12~16 segment rod 모델.
- 중력, 수동 굽힘, 신장, 비틀림, 감쇠, 단면 변화.
- 고정된 뿌리와 자유 끝 시험.

**종료 조건:** 팔이 중력으로 처지고, 목표 신장/굽힘이 연속적으로 일어나며 NaN 없이 안정적으로 작동.

### Phase 2 — 8개 팔 + 몸통

- 몸통 체적 모델, 8개 뿌리 연결.
- 팔 사이의 힘/반작용 및 몸통 변형.
- 팔별 조작 입력.

**종료 조건:** 한 팔을 당기면 몸통이 반응하고, 다른 팔도 물리적으로 연결된 거동을 보임.

### Phase 3 — 통합 세계·접촉·마찰

- 바닥, 정적 장애물, 동적 강체, 자기 충돌, 문어 간 충돌.
- 2문어 + 여러 오브젝트 데모.
- 동적 물체에 같은 중력·접촉 프레임 적용.

**종료 조건:** 문어끼리 서로 밀고, 상자를 밀고, 오브젝트의 반작용이 문어로 돌아옴.

### Phase 4 — 빨판·운동 제어·게임플레이

- 접촉 기반 부착과 해제.
- 키 입력→근육 구동.
- 바닥 짚고 끌기/밀기, 물체 잡고 이동하기.
- 각각의 문어를 마우스로 선택하고 힘을 가해 드래그하는 디버그 모드.

**종료 조건:** 지정한 조작으로 실제 접촉·반작용을 이용한 이동이 가능.

### Phase 5 — GameReady 렌더링/피부 변형

- 실제 아트 에셋 연결, GPU 표면 스키닝.
- 몸통 눌림·팔 국소 압착·빨판·피부 재질.
- 물리와 화면의 형상 정합 검증.

**종료 조건:** 물리 변형이 고해상도 모델에 자연스럽게 나타나고 팔 뿌리/빨판의 심한 파손·미끄러짐이 없음.

### Phase 6 — 10마리 성능 최적화

- 1/2/5/10마리 배치 테스트와 최악의 접촉 스트레스 테스트.
- 프로파일링으로 병목 제거.
- LOD, 충돌 가속, 제약 병렬화, GPU 스키닝 적용.

**종료 조건:** 정의한 기준 하드웨어에서 프레임 목표 충족 또는 미달 원인과 개선안을 수치로 명확히 제시.

### Phase 7 — 안정성·회귀 테스트 및 보고

- 고정 시드/고정 입력 로그의 장시간 실행.
- 실패 재현 및 회귀 테스트.
- 성능·관통·체적·질량중심/운동량 오차 보고.

**종료 조건:** 통과한 테스트와 남은 실패가 문서/실행 로그로 구분됨.

| T05 | 바닥 접촉 | 비관통·마찰 | 최대 관통 깊이/접촉 안정성 수치 기록 |
| T06 | 몸통 당김 | 힘 전달 | 팔의 구동에 몸통이 반응 |
| T07 | 상자 밀기 | 양방향 힘 | 문어와 상자 모두 접촉 반응 |
| T08 | 빨판 고정·파단 | 유한한 부착력 | 부착력 임계치 아래 유지/초과 시 해제 |
| T09 | 자기 충돌 | 팔 얽힘 | 인접 예외 외의 관통 감시 |
| T10 | 문어 간 충돌 | 반작용 | 두 문어의 위치·속도 반응 확인 |
| T11 | 10마리 스트레스 | 실시간성 | 정해진 HW에서 평균/p95/p99 프레임 시간 보고 |
| T12 | 장시간 시뮬레이션 | 수치 안정성 | 최소 10,000 fixed ticks 동안 NaN/Inf 없음 |
| T13 | 시각 변형 | 렌더-물리 정합 | 팔 뿌리, 빨판, 눌림, 틈 통과 육안 검증 |
| T14 | 회귀 테스트 | 기존 오류 재발 방지 | 재현 시나리오의 수정 전후 결과 기록 |

**주의:** 중력 등 외력이 작용하는 열린 계에서 문어 두 마리의 총 선운동량이 항상 일정할 필요는 없다. 접촉 반작용의 일관성은 접촉 전후의 국소 임펄스 및 외력을 포함하여 검증해야 한다.

## 13. 개발 결정 원칙: 사실성과 성능의 균형

| 선택지 | 이점 | 비용/한계 | 선택 기준 |
|---|---|---|---|
| 본 기반 애니메이션 | 매우 빠름 | 실제 접촉 변형·반작용 제한 | 원거리 외형 보조 |
| 단순 질점-스프링 | 쉽고 빠름 | 체적 유지·비틀림 제어 어려움 | 초기 실험/참고 |
| 고해상도 3D FEM | 재료역학 모델링에 적합 | 실시간 접촉과 10마리에서 고비용 가능 | 제한적 국부 정밀화 |
| MPM | 큰 변형 처리에 유리 | 구현·GPU/메모리 비용 큼 | 필요성과 예산 입증 시 |

완전한 연속체 3D 체적 계산은 **처음부터 전역 적용하지 않는다**. 먼저 측정하고, 필요성과 성능 여유가 확인된 영역만 정교화한다.

## 14. 구현 우선순위와 금지사항

### 필수(P0)

- 팔 8개가 실제 물리로 움직이고 몸통에 연결됨.
- 중력, 바닥, 동적 물체, 문어-문어 충돌.
- 양방향 접촉 힘과 운동량 전달.
- 키 입력으로 팔별 능동 구동 가능.
- 2마리 데모에서 기본 조작 가능.
- 기본 빌드/실행/테스트 자동화.

### 중요(P1)

- 국소 체적 보존과 단면 변형.
- 빨판 부착.
- 몸통 체적 변형.
- 표면 스키닝/질감.
- 10마리 성능 최적화 및 스트레스 테스트.

### 고급(P2)

- 정교한 피부 압착과 좁은 틈 통과.
- 더 실제적인 근육 물성/점탄성.
- 물 환경에서의 유체역학·제트 추진·부력.
- 적응적 세분화/고급 체적 솔버.

### 금지사항

1. 입력을 좌표 순간이동으로 처리한 뒤 '물리 기반 제어'라고 주장하지 않는다.
2. 시각적 메시만 늘리고 실제 충돌체는 변형되지 않는 상태를 '완전한 형태 변형'으로 포장하지 않는다.
3. 문어와 물체가 서로 영향을 주지 않는 일방향 충돌 처리를 하지 않는다.
4. Godot와 C++의 각기 다른 물리 솔버가 독립적으로 움직이게 방치하지 않는다.
5. 화면/실행/벤치마크 검증 없이 '60 FPS 성공', '완료', '통과'라고 보고하지 않는다.
6. 고품질 원본 모델이 있다면 검토 없이 임의의 단순 구체/캡슐 모델로 최종 시각물을 대체하지 않는다(물리 디버그 프록시에는 허용).
7. 사용자의 기존 변경사항을 삭제하거나 덮어쓰지 않는다.

## 15. 최종 산출물

GPT/코딩 에이전트는 다음을 실제 산출물로 남겨야 한다.

1. **재현 가능한 프로젝트**: 소스, 빌드 구성, 실행 스크립트, 의존성 버전.
2. **물리 엔진 코드**: 문어 팔/몸통/강체/접촉/마찰/빨판의 통합 시뮬레이션.
3. **플레이 가능한 데모**: 바닥 + 여러 물체 + 문어 2마리, 팔별 키 조작, 각 문어 선택·드래그, 중력, 상호작용.
4. **성능 시나리오**: 1/2/5/10마리 실행 및 로그 자동 수집.
5. **회귀 테스트**: 기존 오류와 새 충돌/수치 안정성 시나리오.
6. **검증 보고서**: 통과/실패/미검증 구분, 실행 명령, 측정 수치, 사용 하드웨어, 화면/영상/로그 링크 또는 경로.
7. **기술 문서**: 구조, 파라미터 의미와 기본값, 성능 병목, 다음 과제.

최종 보고서의 각 항목은 다음 상태 중 하나로 표시한다.

- `PASS`: 실제 실행·검증됨(증거 첨부).
- `FAIL`: 실행했으나 실패(재현 절차 및 로그 첨부).
- `NOT TESTED`: 아직 검증하지 않음.
- `PARTIAL`: 기능 일부 구현, 합격 기준 일부만 충족.

## 16. 코딩 GPT에게 줄 실행 지시문

> 이 명세서를 최우선 기술 요구사항으로 사용하여 문어 시뮬레이터 게임을 설계·구현·검증하라. 기존 저장소가 있으면 README, 진행상황, 이슈, 코드와 GameReady 에셋을 먼저 조사하고 변경사항을 보존하라. 문어는 각각 8개 팔을 가진 능동 근육성 연속체이며, 팔은 Rod 기반 이산 모델과 XPBD 제약으로 굽힘·신장·비틀림·체적 변형을 계산한다. 몸통은 저해상도 체적 변형체로 처리한다. 문어 자신·문어끼리·강체·바닥 사이의 충돌, 마찰, 부착, 반작용을 동일한 C++ 물리 세계에서 해결하라. Godot는 입력·렌더링·UI 담당으로 분리하고, 고해상도 외형은 GPU 스키닝으로 변형하라. 키 입력은 팔별 근육 활성과 목표 곡률/신장/강성을 조절해야 하며, 좌표 순간이동으로 대체하지 마라. 우선 2마리 데모를 완성하고 최종적으로 10마리 60FPS를 목표로 측정·최적화하라. Phase별로 실제 빌드·테스트·실행을 거치고, PASS/FAIL/PARTIAL/NOT TESTED를 로그와 수치 근거로 보고하라. 새로운 설계 제안만 하고 멈추지 말고 구현과 검증까지 수행하라.

## 17. 관련 문헌 및 검토할 키워드

문헌은 구현의 출발점이며, 이 문서의 초기 수치·성능 목표가 특정 논문에서 검증되었다는 뜻이 아니다.

- **XPBD**: Macklin, Müller, Chentanez, *XPBD: Position-Based Simulation of Compliant Constrained Dynamics* (2016).
- **Small Steps in Physics Simulation**: Macklin et al. (2019), 서브스텝과 위치기반 시뮬레이션의 안정성.
- **Cosserat Rod**: shearable/extensible rod dynamics, discrete elastic rods, rod frames, active bending/twist.
- **Octopus arm mechanics**: muscular hydrostat, transverse/longitudinal/oblique musculature, active stiffness, hydrostatic volume preservation.
- **Soft robotics**: continuum robot actuation, tendon/muscle-inspired inverse control, suction/contact locomotion.
- **Rendering**: dual quaternion skinning, cage-based deformation, dynamic mesh skinning, procedural suckers, PBR/SSS.

**핵심 설계 한 줄:** *고해상도 3D 체적 물리를 전부 계산하는 대신, 팔의 능동 연속체 운동·국소 체적 보존·통합 접촉 반작용은 CPU 물리에서 계산하고, 고품질 외형은 GPU 렌더링으로 재구성하는 하이브리드 구조를 사용한다.*
