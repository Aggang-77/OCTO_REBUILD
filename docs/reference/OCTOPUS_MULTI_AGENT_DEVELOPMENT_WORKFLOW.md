# OCTO — Astra · Sol · Terra 다중 에이전트 개발 운영 지침

> 문서 유형: 문어 시뮬레이터 프로젝트의 AI 협업·작업 분배·통합 검증 지침  
> 함께 읽을 문서: `OCTOPUS_SIMULATOR_TECHNICAL_SPEC.md`  
> 적용 대상: 기존 OCTO 저장소 및 향후 확장 개발  
> 핵심 전략: **Astra가 전체 아키텍처와 통합 책임을 맡고, Sol/Terra가 명확한 경계의 하위 작업을 병렬로 구현·검증한다.**

---

## 0. 이 문서를 받은 GPT에게

이 문서는 단순한 역할 제안이 아니라 **실제로 여러 AI 작업자를 운영하기 위한 절차서**다. 기술적 기능·성능·물리적 요구사항은 `OCTOPUS_SIMULATOR_TECHNICAL_SPEC.md`를 따른다.

- `Astra`, `Sol`, `Terra`는 이 프로젝트에서 정한 **작업 역할 이름**이다. 각 모델의 실제 코딩 성능, 실행 환경, 도구 접근 권한, 사용량 한도, 컨텍스트 길이가 이름만으로 보장되지는 않는다. 실제 사용 가능한 기능을 확인하고 배정한다.
- 모든 에이전트는 현재 코드·문서·빌드 상태를 확인해야 한다. 구현하지 않은 기능을 구현했다고 보고하거나, 실행하지 않은 테스트를 통과했다고 보고하면 안 된다.
- 주어진 저장소의 원본 변경, GameReady 모델, Godot 장면, 테스트 및 사용자 작업을 보존한다.
- **에이전트가 여럿이라고 해서 같은 파일을 동시에 편집하도록 하지 않는다.** 병렬화는 분리 가능한 작업과 파일 소유권이 명확할 때만 수행한다.
- 설계 문서만 계속 추가하지 말고, 각 작업의 종료 조건을 **병합 가능한 코드와 실행 증거**로 정의한다.

## 1. 역할 배분

| 역할 | 책임 | 주된 작업 | 피해야 할 일 |
|---|---|---|---|
| **Astra — 총괄 아키텍트/통합 책임자** | 프로젝트 방향·핵심 설계·경계 결정·최종 품질 | 기존 상태 조사, 시스템 구조, 인터페이스 계약, 우선순위, 작업 분배, 어려운 충돌 해결, 통합 빌드·성능 검증 | 세부 구현을 전부 혼자 떠안아 병렬화 이점을 없애는 일 |
| **Sol — 핵심 알고리즘 구현 담당** | 제한된 범위의 난도 높은 계산·알고리즘 구현 | Rod/XPBD 제약, 솔버 수치 안정성, 충돌 알고리즘, 물리 테스트 등 **배정된 하나의 모듈** | 전체 물리 API와 다른 담당자 소유 파일을 독자적으로 변경하는 일 |
| **Terra — 독립 기능/도구/검증 담당** | 경계가 뚜렷한 기능을 끝까지 완성 | Godot 입력·UI·렌더링 브리지, 데모 장면, 테스트 자동화, 프로파일러, 문서화 등 **배정된 하나의 모듈** | 통합 설계에 동의 없이 독자적으로 물리 세계를 새로 만드는 일 |

위 표는 **기본 추천 배치**일 뿐이다. 실제 모델별 강점·도구 접근성에 따라 Sol과 Terra의 업무는 서로 바꿀 수 있다. 핵심은 모델 서열이 아니라 **설계 책임과 구현 책임을 분리하는 것**이다.

### Astra가 최종 책임을 져야 하는 결정

1. `PhysicsWorld`가 전체 동적 물체를 관리하는 방식과 시뮬레이션 갱신 순서.
2. 물리 상태·렌더 상태·Godot GDExtension 사이의 API 및 메모리 소유권.
3. 팔의 Rod 요소, 몸통 체적 요소, 강체, 접촉, 빨판이 공유하는 상태 표현.
4. 물리 단위계, 좌표계, 시간 간격, 서브스텝, 제약 순서와 수치 허용 오차.
5. 성능 목표·벤치마크 조건·작업별 합격 기준.
6. 공개 API 변경 승인, 모듈 통합 순서, 충돌 해결, 최종 릴리스 판정.

**운영 원칙:** Astra는 프로젝트 관리만 하는 역할이 아니다. 가장 위험하거나 모듈 간 결합이 큰 코드는 직접 구현하거나 최소한 재현 테스트를 직접 실행해야 한다.

## 2. 개발 시작 전 필수 절차

각 에이전트는 작업을 시작하기 전에 다음 사항을 확인한다.

1. 실제 저장소 경로, 현재 Git 브랜치 및 커밋 SHA, `git status --short`를 기록한다.
2. `README.md`, `docs/progress/STATUS.md`, `docs/issues/`, `CMakeLists.txt`, Godot 프로젝트와 관련 구현을 읽는다. 파일이 없다면 없다고 적는다.
3. 기존 실행 가능한 데모, 빌드 명령, 테스트 명령, Godot 버전, C++ 툴체인, GLB/GameReady 에셋의 위치를 확인한다.
4. 현재 통과/실패하는 테스트의 **기준선(baseline)** 을 확정한다. 검증 가능한 실행 환경이 없다면 그 사실을 적는다.
5. 이미 존재하는 로컬 변경사항을 보호한다. 명시적 승인 없이 `git reset --hard`, `git clean -fd`, 강제 체크아웃, 무분별한 `stash pop`, 강제 푸시를 사용하지 않는다.
6. 사용자가 별도로 요청하지 않았다면 작업 기록을 남기기 위한 커밋은 허용하되, 원격 푸시는 기존 프로젝트 정책에 맞춰 처리한다.

### 기준선 기록 양식

```text
Repository: <absolute path or URL>
Base branch: <name>
Base commit: <SHA>
Working tree: <clean / modified + list>
Build command: <exact command>
Test command: <exact command>
Godot run command: <exact command>
Baseline PASS: <test IDs + evidence>
Baseline FAIL: <test IDs + evidence>
Baseline NOT TESTED: <test IDs + reason>
Assets checked: <actual paths>
Environment: <OS / compiler / CMake / Godot / CPU / GPU>
```

## 3. 개발 구조: 먼저 계약, 다음 병렬 구현, 마지막 통합

```text
                     [사용자 요구 + 기술 명세서]
                                 |
                                 v
                 [Astra: 저장소 분석 / 시스템 설계]
                                 |
               [인터페이스 계약 / 테스트 기준 고정]
                                 |
             +-------------------+-------------------+
             |                                       |
             v                                       v
  [Sol: 물리 핵심 모듈]                    [Terra: 독립 모듈/테스트]
  - Rod / XPBD                             - Godot 브리지 / 입력
  - 접촉 / 반작용                          - 시각 스키닝 / UI
  - 단위·회귀 테스트                       - 데모 / 자동화 / 벤치마크
             |                                       |
             +-------------------+-------------------+
                                 |
                                 v
                   [Astra: 코드 리뷰 / 충돌 해결]
                                 |
                                 v
                    [통합 빌드 / 실기동 / 회귀]
                                 |
                      [성능·시각적 증거 확인]
                                 |
                [다음 작업 분배 또는 릴리스]
```

중요: 여러 작업자가 각각 별개의 완성품을 만드는 구조가 아니다. **하나의 게임과 하나의 C++ 물리 세계를 공동으로 구현**해야 한다.

## 4. 모듈 소유권과 병렬화 경계

아래는 추천 **모듈 경계**다. 실제 저장소 파일 구조가 다르면 Astra가 조사 후 매핑하고 이를 문서화한다.

| 모듈/기능 | 기본 담당 | 의존성 | 완료 조건 |
|---|---|---|---|
| 핵심 데이터 계약 (`SimulationState`, `PhysicsWorld` API) | **Astra** | 없음 | 컴파일되는 헤더/인터페이스 + 계약 테스트 |
| Rod 요소와 XPBD 제약 | **Sol** | 핵심 데이터 계약 | 굽힘·신장·비틀림·체적 보존 테스트 |
| 충돌 broadphase/narrowphase | **Sol** 또는 별도 작업자 | 충돌체 인터페이스 | 바닥·물체·자기 충돌 후보 및 접촉 테스트 |
| 몸통 체적 변형/P2V | **Sol** 또는 별도 작업자 | 공유 물리 상태 | 눌림·체적·힘 전달 테스트 |
| Godot GDExtension 브리지 | **Terra** | 공개 PhysicsWorld API | 빌드/로드/좌표 전달 테스트 |
| 팔별 키 입력 및 마우스 조작 | **Terra** | 명령/입력 API | 8개 팔 독립 조작 + 2마리 선택 테스트 |
| 데모 장면/모델/셰이더 | **Terra** | 렌더 상태 계약 | 원본 GameReady 모델 실행 화면 검증 |
| 성능 측정·자동 회귀·CI | **Terra** | 실행 대상 | 재현 가능한 명령과 로그 파일 생성 |
| 통합 솔버/강체 접촉 연결 | **Astra** | 물리 모듈 | 단일 세계의 양방향 반작용 검증 |
| 최종 10마리 성능 조정 | **Astra 총괄**, 실행은 분배 | 모든 모듈 | 1/2/5/10마리 실측 결과 |

### 동시 작업 가능성 규칙

- **병렬 가능:** 서로 다른 소스 디렉터리, 고정된 인터페이스, 독립 테스트가 있는 두 작업.
- **조건부 가능:** 같은 인터페이스를 이용하지만 API를 변경하지 않는 두 작업.
- **병렬 금지:** 동일한 헤더/API 수정, 동일한 Godot 장면 편집, 동일한 빌드 설정 동시 변경, 동일한 충돌 솔버 루프 동시 수정.
- 공유 파일 변경이 필수라면 **Astra가 변경을 선행**해 공통 기반 커밋을 만든 후 작업을 다시 분배한다.
- 구현자가 API 변경이 필요하다고 판단하면 임의로 전체 시스템을 고치지 말고 **변경 요청서**를 전달한다.

## 5. 권장 진행 순서와 실제 작업 분할

### Wave 0 — 현상 파악 및 경계 확정 (Astra 주도)

- 현재 프로젝트의 물리 모델·GameReady 에셋·Godot 연결·성능 병목·기존 오류를 분석한다.
- 기존 `STATUS.md`와 이슈에 있는 미완료 항목, 접촉 오류, 수치 발산, 렌더링 불일치를 확인한다.
- 단일 `PhysicsWorld` API, 게임 입력 명령, 렌더 상태 교환 구조를 명시한다.
- 공통 테스트와 성능 기록 형식을 먼저 마련한다.

**종료 조건:** 기준선 로그, 변경할 파일 목록, 작업 카드, 인터페이스 계약이 존재한다.

### Wave 1 — 최소 수직 슬라이스 (분업)

- **Sol:** 팔 1개의 Rod/XPBD 운동과 중력·굽힘·신장 단위 테스트.
- **Terra:** 더미 시뮬레이션 데이터를 이용한 Godot 로딩·입력·시각 브리지 검증.
- **Astra:** 두 모듈을 하나로 통합해 실제 팔 1개를 화면에서 물리적으로 움직이고 접촉시키는 실행 테스트.

**종료 조건:** 장식 애니메이션이 아닌 C++ 물리 결과가 Godot 화면에 나타난다.

### Wave 2 — 팔 8개·몸통·상호작용 (분업)

- **Sol:** 팔/몸통 연결, 능동 강성, 체적 제약 및 접촉 알고리즘.
- **Terra:** 팔별 키 매핑, 문어 선택, 마우스 목표/힘 입력, 기본 데모 씬.
- **Astra:** 단일 물리 세계의 강체·연체·접촉 솔버 통합, 양방향 반작용 검증.

**종료 조건:** 바닥과 물체가 있는 씬에서 팔 8개가 각자 구동하고 문어의 몸통을 움직일 수 있다.

### Wave 3 — 2마리 실제 데모·형태 변형 (분업)

- **Sol:** 문어-문어 충돌, 자기 충돌, 몸통 및 팔의 국소 압착, 빨판 부착 제약.
- **Terra:** 2마리 배치, 각각 독립 조작/마우스 드래그, GameReady 모델·피부·빨판 표현.
- **Astra:** 복잡한 접촉에서 NaN, 관통, 접촉 발산을 막고 실제 화면과 수치 로그를 검증한다.

**종료 조건:** 문어 2마리·바닥·여러 동적 오브젝트가 동일한 C++ 물리 세계에서 작동한다.

### Wave 4 — 최적화 및 종료 검증 (분업)

- **Sol:** 프로파일에 근거한 물리 병목 개선(충돌 가속, 제약/데이터 레이아웃, 접촉 캐시 등).
- **Terra:** 1/2/5/10마리 자동 벤치마크, 프레임 시간 수집, 화면 녹화/스크린샷, 재현 스크립트.
- **Astra:** 전체 물리·시각·게임플레이 회귀, 10마리 성능 목표 검증, 이슈 우선순위 결정.

**종료 조건:** 기술 명세서의 테스트 ID별 결과와 재현 가능한 성능 보고서가 있다.

### 작업 선택 원칙

실제 기존 프로젝트가 이미 Wave 2에 도달해 있다면 Wave 0 기준선 확인 후 **누락된 부분만 수행**한다. 이미 완성된 기능을 처음부터 다시 작성하지 않는다. 병목이 아직 측정되지 않았다면 성급하게 솔버 전체를 경량화하지 않는다.

## 6. 작업 카드(Task Contract) — 모든 위임의 필수 형식

Astra는 Sol/Terra에게 추상적인 한 줄 지시를 보내지 않는다. 각 위임은 아래 내용을 포함한다.

```markdown
# TASK: <ID> — <작업 제목>

## 목적
<최종 사용자가 체감할 결과 + 기술적 목적>

## 기준선
- Repository / worktree: <경로>
- Base branch / SHA: <브랜치, 커밋>
- 관련 명세: <문서 섹션>
- 관련 이슈/실패: <재현 절차 또는 로그>

## 담당 파일/모듈
- 수정 허용: <명시적인 경로 목록>
- 변경 금지: <공유 인터페이스·다른 담당 파일>

## 고정된 인터페이스
- 입력 API: <타입, 단위, 좌표계, 호출 주기>
- 출력 API: <타입, 소유권, 오류 동작>
- 의존성 및 버전: <필요한 조건>

## 필수 구현
1. <작게 쪼갠 작업 1>
2. <작업 2>
3. <작업 3>

## 합격 기준
- <자동화 테스트 및 기대 결과>
- <실행해야 할 명령>
- <수치 허용 오차 및 성능 조건>
- <필요한 Godot 화면/로그 검증>

## 인계 산출물
- 작업 브랜치 및 커밋 SHA
- 변경 파일/코드 설명
- 실행 명령과 실제 출력 로그
- PASS / FAIL / PARTIAL / NOT TESTED
- 미해결 문제 및 다음 담당자 요청사항

## 주의사항
- 사용자 기존 변경 보존
- 다른 담당 파일 무단 편집 금지
- 테스트 없이 통과 주장 금지
- 실패하면 재현 가능한 최소 사례 제출
```

**작업 규모:** 가능한 한 *하나의 독립적인 결과와 검증*으로 끝나는 단위로 나눈다. 예: `접촉 후보 가속 구조 구현`은 좋은 작업이고 `물리 엔진을 완성해라`는 병렬 구현 작업으로는 너무 크다.

## 7. Git 협업: 작업 브랜치와 worktree

가능하면 한 저장소를 공유하되 **각 에이전트에게 별도의 Git worktree와 브랜치를 배정**한다.

```text
OCTO/                    # Astra 통합용 작업 트리
OCTO-sol-rod/            # Sol: feat/rod-constraints
OCTO-terra-godot/        # Terra: feat/godot-input-bridge
```

예시 명령(실제 저장소 경로·기준 브랜치 확인 후 실행):

```bash
# 기준 브랜치에서, 작업 트리가 안전한 상태임을 확인한 뒤
 git status --short
 git rev-parse HEAD

# 서로 다른 작업 디렉터리와 브랜치를 생성
 git worktree add ../OCTO-sol-rod -b feat/rod-constraints
 git worktree add ../OCTO-terra-godot -b feat/godot-input-bridge
```

**주의:** 이 예시는 새로운 브랜치가 생성 가능한 경우에만 적용한다. 이미 같은 이름의 브랜치가 있거나 현재 작업 트리가 미정리 상태라면 상태를 확인하고 충돌하지 않는 안전한 절차를 선택한다. 공유 작업 트리에서 여러 에이전트가 동시에 `git checkout`하지 않는다.

### 병합 절차

1. 담당자가 **자기 브랜치**에서 테스트·커밋한 후 결과를 인계한다.
2. Astra가 diff를 검토하고 공유 API 변경 여부를 확인한다.
3. 기존 변경을 보존하면서 기준 브랜치에 병합한다. 충돌 시 함수 단위의 의도를 확인해 해결한다.
4. **병합 직후 전체 빌드 + 핵심 회귀 테스트**를 실행한다.
5. 두 번째 브랜치는 최신 통합 기준선으로 갱신하거나 충돌을 확인한 뒤 병합한다.
6. 병합 통과 후에만 `STATUS.md`의 완료 상태를 갱신한다.

충돌이 많고 연속 통합이 필요한 작업은 병렬 배정하지 않는다. Git 명령을 실행할 권한이나 공유 저장소 접근이 없는 채팅 세션에서는 각 담당자가 **패치/커밋/파일 목록과 테스트 로그**를 만들어 Astra에 전달한다. 여러 GPT 채팅 사이에 파일·로컬 상태가 자동 공유된다고 가정하지 않는다.

## 8. 인터페이스 계약 예시

아래 코드는 **개념적 계약 예시**이며 기존 저장소의 API를 확인하기 전까지 실제 구현으로 확정하면 안 된다.

```cpp
struct MuscleCommand {
    OctopusId octopus;
    uint8_t arm_index;          // 0..7
    float target_curvature;     // 단위와 부호는 계약 문서에 명시
    float target_extension;     // 기준 길이에 대한 비율 등 명시
    float active_stiffness;     // 범위와 물성 대응 정의
    bool attach_requested;
};

struct PhysicsWorld {
    void enqueue_command(const MuscleCommand& command);
    void step(float fixed_dt_seconds);
    RenderSnapshot make_render_snapshot() const;
};
```

Astra는 실제 계약에 다음을 명시해야 한다.

- 월드 좌표계, 길이 단위(m 등), 질량·시간 단위, 중력 벡터.
- `fixed_dt`와 서브스텝 적용 위치, 렌더 보간 방법.
- 팔/몸통/강체의 인덱스 안정성, 데이터 수명, 스레드 안전성.
- 충돌 필터, 연속된 팔 구간의 자기 충돌 예외, 접촉 캐시의 갱신 정책.
- 렌더용 상태와 물리 상태의 불변성 및 GPU 업로드 시점.
- 키 입력에 대한 명령 주기, 큐 정책, 마우스 드래그를 힘/제약으로 변환하는 규칙.

**핵심:** Sol은 내부 알고리즘을 바꿀 수 있지만 외부 계약을 깨면 안 된다. Terra는 렌더/입력 기능을 고도화할 수 있지만 물리 결과를 화면에서 임의로 덮어쓰면 안 된다.

## 9. 통합 게이트와 검증 증거

| 게이트 | 검사 책임 | 통과 기준 |
|---|---|---|
| G0 기준선 확보 | Astra | 저장소·브랜치·원본 파일·기존 실패 확인 |
| G1 모듈 단위 검증 | 해당 담당자 | 수정 모듈 빌드, 관련 단위 테스트 PASS |
| G2 인터페이스 호환 | Astra | 공개 API·단위·상태 소유권 계약 준수 |
| G3 통합 물리 검증 | Astra | 중력·충돌·반작용·문어 2마리 확인 |
| G4 화면 검증 | Terra 구현, Astra 확인 | 실제 Godot 실행에서 GameReady 모델/변형 확인 |
| G5 회귀 검증 | Astra | 기존 재현 이슈 재발 없음 및 지정 시드 테스트 |
| G6 성능 검증 | Terra 측정, Astra 판정 | 1/2/5/10마리 실측; 기준 HW·평균/p95/p99 명시 |

**검증 상태 정의**

- `PASS`: 실제 실행한 명령·환경·로그가 있고 합격 기준을 만족함.
- `FAIL`: 실제 실행했으나 기준 미달, 로그와 재현 절차가 있음.
- `PARTIAL`: 일부 조건만 만족함.
- `NOT TESTED`: 실행하지 않았거나 테스트 환경이 없음.

한 에이전트가 단위 테스트를 통과했다고 해서 전체 데모가 통과한 것은 아니다. **통합 성공 선언 권한은 Astra**에게만 있으며 Astra도 실제 실행 증거가 없으면 `NOT TESTED`로 기록한다.

### 최소 로그 출력

```text
Task / commit / branch:
Build: PASS|FAIL|NOT TESTED
Unit tests: PASS|FAIL|NOT TESTED (x/y)
Integration tests: PASS|FAIL|NOT TESTED (IDs)
Godot visual run: PASS|FAIL|NOT TESTED
Physics metrics: max penetration / volume error / NaN count
Performance: HW / resolution / octopus count / avg / p95 / p99
Known regressions:
Evidence paths:
Next action:
```

## 10. 실패·지연을 줄이는 운영 규칙

1. **작업을 지나치게 넓게 주지 않는다.** `팔 물리 전체 완성`보다 `Rod 비틀림 제약과 회귀 테스트`처럼 결과를 검증할 수 있도록 쪼갠다.
2. **계약이 안정되기 전에는 병렬화하지 않는다.** API가 계속 바뀌면 통합 비용이 절감한 시간보다 커진다.
3. **가장 느리거나 위험한 경로를 먼저 구현한다.** 특히 2마리 이상 접촉과 단일 물리 세계의 양방향 힘 전달.
4. **물리 루프를 한 사람만 소유한다.** 여러 에이전트가 동일한 XPBD 제약 루프를 각각 수정하면 오류 원인 추적이 어려워진다.
5. **실측 전 경량화를 과도하게 진행하지 않는다.** 접촉 broadphase가 병목인지, 솔버 반복인지, Godot 렌더링인지 분리 측정한다.
6. **기능 구현과 검증을 동시에 분배할 수 있다.** 단, 테스트 명세는 담당 구현자가 임의로 완화할 수 없도록 Astra가 관리한다.
7. **통합 중 실패하면 새 기능을 중단하고 회귀를 고친다.** 깨진 기준선 위에 계속 기능을 쌓지 않는다.
8. **문서에는 실제 상태를 쓴다.** 구현 완료, 시험 통과, 화면 검증, 성능 달성은 서로 다른 상태다.
9. **사용자 요구 우선순위를 준수한다.** 좋은 데모만 만들고 P0 오류와 10마리 실시간 성능을 방치하지 않는다.
10. **역할 배치 자체를 검증한다.** 특정 모듈에서 Sol/Terra 중 누가 더 안정적으로 작업하는지 실제 빌드·테스트 및 통합 소요를 보고 다음 분배에 반영한다.

충돌이 발생하면 Astra가 **기존 구현과 사용자 요청을 확인**하여 계약·기술 명세·코드 중 무엇을 변경해야 할지 결정하고, 변경 사유와 영향 범위를 기록한다. 문서에 적혔다는 이유만으로 현존하는 작동 코드를 무조건 교체하지 않는다.

## 12. GPT에 바로 전달할 프롬프트

### 12.1 Astra — 전체 총괄 프롬프트

> 너는 OCTO 프로젝트의 **총괄 아키텍트이자 최종 통합 책임자(Astra)** 다. 함께 제공한 `OCTOPUS_SIMULATOR_TECHNICAL_SPEC.md`와 `OCTOPUS_MULTI_AGENT_DEVELOPMENT_WORKFLOW.md`를 준수하라. 우선 실제 저장소의 README, 상태 문서, 이슈, 소스, Godot/GameReady 에셋, Git 변경사항, 빌드/테스트 기준선을 검증하라. 단일 C++ 물리 세계를 중심으로 공유 API와 모듈 소유권을 확정하고, **Sol/Terra가 병렬로 구현할 수 있는 독립 작업 카드**를 작성하라. 위험도가 큰 구조·물리 통합과 브랜치 병합은 네가 책임져라. 각 담당 결과를 실제 빌드·실행·테스트로 검증하고, Godot 실제 화면·10마리 성능·기존 오류 회귀까지 확인하라. 사용자 변경사항을 보존하며 무단 초기화하거나 완료를 추정하지 마라. 작업할 수 있는 도구가 있다면 계획 수립에 그치지 말고 직접 개발·통합·검증하라. 마지막에 작업별 담당, 커밋, PASS/FAIL/PARTIAL/NOT TESTED, 재현 명령, 로그, 성능 수치, 미완료 작업을 보고하라.

### 12.2 Sol — 물리/알고리즘 담당 프롬프트

> 너는 OCTO 프로젝트의 **Sol 구현 담당자**다. Astra가 지정한 **단 하나의 작업 카드**와 고정 API·담당 파일 범위만 수행하라. 기존 코드와 테스트를 먼저 읽고 작업 브랜치/커밋 SHA를 확인하라. 물리적 정확성(단위·시간 적분·접촉 반작용), 수치 안정성, 실제 성능을 중시하며, 관련 단위/회귀 테스트를 추가하라. 다른 담당 파일이나 공개 인터페이스 변경이 필요하면 먼저 변경 제안과 이유를 보고하고, 승인 없이 광범위하게 수정하지 마라. 구현 후 실제 빌드·테스트 명령, 결과 로그, 변경 파일, 커밋 SHA와 미해결 사항을 Astra에 인계하라. 검증하지 못한 내용은 `NOT TESTED`로 표시하라.

### 12.3 Terra — 독립 기능/검증 담당 프롬프트

> 너는 OCTO 프로젝트의 **Terra 구현 담당자**다. Astra가 지정한 **단 하나의 작업 카드**를 담당하며, 물리 세계의 API와 입력·렌더링 분리 원칙을 준수하라. Godot/게임 입력/시각화/데모/테스트 자동화 중 배정된 모듈을 완성하고, 실제 게임 실행 및 눈에 보이는 결과로 검증하라. C++ 물리 결과를 임의 애니메이션으로 대체하거나 기존 GameReady 모델을 무단 교체하지 마라. 수정 허용 파일 범위를 넘지 말고, 변경 결과와 테스트·스크린샷/로그·커밋 SHA를 명확히 인계하라. 검증하지 못한 내용은 `NOT TESTED`로 표시하라.

### 12.4 Astra — 결과 병합 및 통합 검증 프롬프트

> Sol과 Terra의 결과를 병합·검증하라. 먼저 각 브랜치/커밋의 출처와 변경 파일을 확인하고 사용자 로컬 변경사항을 보호하라. 공유 API, 물리 세계, Godot 장면의 호환성을 검토해 순차적으로 통합하라. **각 병합 직후 실제 빌드와 회귀 테스트**를 실행하고 실패 시 해당 변경의 책임 범위를 확인하라. 데모 2마리의 팔별 조작·중력·오브젝트/문어 간 충돌·반작용과 10마리 실시간 성능을 실제로 검증하라. 결과는 근거 로그와 함께 PASS/FAIL/PARTIAL/NOT TESTED로 기록하고 `docs/progress/STATUS.md`를 갱신하라. 완성되지 않은 기능을 마감 처리하지 마라.

## 13. 권장 최종 운영 방식

- **Astra:** 시스템 설계 → 작업 카드 작성 → 병렬 담당 승인 → 위험한 통합 개발 → 코드 리뷰 → 순차 병합 → 통합 테스트 및 성능 판정.
- **Sol:** 명세가 고정된 물리/알고리즘 모듈 한 개를 **코드+테스트** 단위로 완료.
- **Terra:** 독립 기능/게임 연결/자동화 모듈 한 개를 **실행 결과+테스트** 단위로 완료.
- **사용자:** 게임의 조작감, 시각적 질감, 생체 사실성, 허용 가능한 성능·범위의 최종 우선순위를 결정.

**한 문장 요약:** *Astra는 프로젝트 전체의 정합성에 책임을 지고, Sol/Terra는 명확하게 격리된 하위 기능을 실제 코드와 검증으로 완성하며, 최종 완료 여부는 통합 실행 결과로만 판단한다.*
